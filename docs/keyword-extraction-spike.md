# Image keyword extraction from IPTC and XMP on upload (AB#54)

**Status: scaffolded — awaiting the owner-run measurement.** The checklist, the
library research, and the docs-based hypotheses below are ready. The three
Lightroom exports and the non-production Sanity upload are the owner's to run;
the verbatim outputs then fill the _(pending)_ sections and the conclusions
that depend on them.

This is a **time-boxed extraction spike**. It selects no production schema, ships
no dependency, and merges no ingest code (AB#54 AC8). Its only output is this
document, written for **AB#55** ("ADR: image keyword taxonomy and ingest
boundary").

---

## Why this spike

[ADR-0012 §4](adr/0012-dynamic-keyword-gallery-query-contract.md) fixes the
dynamic-query *matching contract* and defers the taxonomy mechanism to AB#55.
[`keyword-query-benchmark.md`](keyword-query-benchmark.md) (AB#65, measured) then
picked the **read** mechanism — materialize the ancestor closure on the medium
(`expandedKeywordIds`). What neither settled is the **ingest** half AB#55 also
owns:

- What a photograph's keywords actually *are* by the time they could be imported —
  the exact fields, their encoding, and whether Lightroom's hierarchy survives an
  export at all.
- Whether Sanity's own upload pipeline captures any of that, or whether a separate
  extraction step is required.
- If a separate step is required: **where** it runs and **what** parses the file.
- Whether the controlled vocabulary AB#56 will build can be *seeded* from a
  Lightroom keyword export rather than typed by hand.

AB#55 cannot decide "the raw imported versus effective curated keyword model",
"the Lightroom/site source-of-truth relationship", or "deterministic re-import
merge/tombstone behavior" (its AC2/AC3) without this evidence. Hence the spike.

## What is being measured (AC1)

Three JPEGs, exported from the same Lightroom catalog with the **same export
preset**, uploaded through the **same** non-production Sanity path:

| File | Keywords in Lightroom | What it isolates |
| --- | --- | --- |
| `control.jpg` | **none** | the baseline — lets every later field be classified as file-derived, generated by Sanity, or absent (AC3) |
| `flat.jpg` | a few **flat** keywords, no parent/child | `dc:subject` / IPTC `Keywords` shape when there is no hierarchy |
| `hierarchical.jpg` | keywords inside a **≥2-level hierarchy**, plus one Finnish-diacritic term, one with a synonym, and one flagged "do not export" | `lr:hierarchicalSubject` shape and how `dc:subject` flattens the same tree; Finnish NFC/NFD encoding (AC6); synonym and "do not export" handling in the file and the keyword-list export (AC5) |

### Known sentinel metadata to set in Lightroom before export

So AC3 can tell "the file carried this" from "Sanity generated this", set every
field below to a **recognisable, non-personal sentinel** on all three images
(identical across the three except for the keywords):

| Lightroom field | Sentinel value to use |
| --- | --- |
| Title | `AB54 SPIKE TITLE` |
| Caption | `AB54 spike caption body.` |
| Copyright | `AB54 spike copyright` |
| Creator / Artist | `AB54 spike creator` |
| Headline | `AB54 spike headline` |
| Keywords — `flat.jpg` | `Landscape`, `Water`, `Winter` (flat, unrelated) |
| Keywords — `hierarchical.jpg` | a ≥2-level hierarchy, **leaves only** applied to the photo: `Nature > Water > Lake`, `Nature > Water > Järvi`, `Places > Finland > Helsinki`. `Järvi` (Finnish for "lake") carries the `ä` diacritic — it exercises AC6's Finnish-character question in both the flattened `dc:subject` value and the hierarchical path. Also configure, in the catalog: a **synonym** on one keyword (e.g. `Järvi` → synonym `Vesistö`), and one keyword with **"Include on Export" unchecked** (e.g. `Työversio`), applied to the photo — so the exported file and the `Export Keywords…` `.txt` both show how each is handled |
| Keywords — `control.jpg` | *(none — remove all)* |

`Järvi`, `Vesistö`, and `Työversio` are ordinary Finnish common nouns, chosen so
the spike can actually observe diacritic encoding, synonym syntax, and the
"do not export" marker rather than only promising to. None of these values is
real archive metadata, so recording them verbatim later is safe (AC7).

> **Why a hierarchy with leaves applied but parents not:** that is the normal
> Lightroom pattern, and it is exactly the case where `dc:subject` (flattened)
> and `lr:hierarchicalSubject` (pathed) diverge — the spike needs to see that
> divergence, not a degenerate case where every node is applied directly.

## Owner checklist

Work top to bottom. Anything in **bold** is a value to record in the _(pending)_
sections further down.

### A. Prepare a throwaway catalog and three source images

1. **Create a new, empty Lightroom catalog for this spike** (`File ▸ New
   Catalog…`). Do the whole spike in it. This matters for AC7: `Export
   Keywords…` in step E.3 dumps the *entire catalog vocabulary*, so run against a
   fresh catalog and that file contains only the spike's own sentinel terms —
   never real client, person, or location keywords. Creating the hierarchy,
   synonyms, and "do not export" flag in a scratch catalog also leaves your real
   catalog untouched.
2. Use images with **no identifiable content and no pre-existing embedded
   metadata**. The project's own six demo photographs
   (`public/gallery/*.webp`) are ideal: `docs/asset-inventory.md` confirms they
   carry no EXIF/XMP/IPTC at all, and they are already cleared for reuse. Any
   three plain landscape frames work.
3. If starting from the `.webp` demos, convert three of them to plain JPEG first
   (any tool; no metadata added), then import those JPEGs into the scratch
   catalog.
4. Name them `control`, `flat`, `hierarchical` so the outputs stay sorted.

### B. Assign keywords + sentinel metadata in Lightroom

1. In Lightroom, set the **sentinel Title / Caption / Copyright / Creator /
   Headline** (table above) on all three.
2. On `flat.jpg`: add the three flat keywords. Make sure none of them sits inside
   a keyword hierarchy in your catalog.
3. On `hierarchical.jpg`: create the keyword hierarchy, apply **only the leaf
   keywords** to the photo (`Lake`, `Järvi`, `Helsinki`, `Työversio`), and
   confirm in the Keywording panel that the parent terms show as implied
   (greyed), not directly applied. Add the synonym (`Järvi` → `Vesistö`) and
   uncheck **Include on Export** for `Työversio`.
4. On `control.jpg`: confirm the Keyword Tags field is empty.

### C. Export — settings to use *and record* (AC2)

Create one export preset and use it for all three. Record every value:

- **Lightroom product** (Lightroom Classic vs Lightroom / "CC") and **exact
  version** (`Help ▸ System Info…`).
- **Operating system** and version; CPU architecture.
- **File Settings:** format **JPEG**, quality, colour space (sRGB), bit depth.
- **Image Sizing:** whether resized; long-edge px if so.
- **Metadata panel — this is the important part:**
  - **Include** dropdown: one of *Copyright Only* / *Copyright & Contact Info
    Only* / *All Except Camera & Camera Raw Info* / **All Metadata**. Record which.
    Run the spike with **All Metadata** so nothing is stripped; note if a more
    restrictive level is what a real workflow would use.
  - **Remove Person Info** — checked? (recommended: yes)
  - **Remove Location Info** — checked? (recommended: yes)
  - **Write Keywords as Lightroom Hierarchy** — **checked?** Record its state.
    Ideally export `hierarchical.jpg` **once with it on and once with it off**
    (`hierarchical-hier-on.jpg` / `hierarchical-hier-off.jpg`) — this toggle is
    the single most decision-relevant export setting for AB#55.
  - Any "Include Synonyms" / keyword-export options present in your version.
- Keep the exported files locally; they are **not committed** (AC7). Only their
  parsed metadata goes in this document.

### D. Upload through the non-production Sanity path (AC1)

1. Use a **non-production** Sanity project **or** a throwaway dataset — never the
   Preview or Production dataset. A dedicated `npx sanity dataset create
   ab54-YYYYMMDD` on the existing dev project is fine; delete it afterwards.
2. Upload via the path a real clone would use — the **Studio asset uploader** is
   the representative one. (If you also have a `@sanity/client`
   `client.assets.upload('image', …)` script handy, capturing both is a bonus,
   but Studio is the one that matters.)
3. **Record each asset's `_id` as you upload it** — one line per file:
   `control.jpg → image-abc123…-jpg`, etc. The `_id` (not the filename) is how
   the capture step below queries the documents back. This matters because the
   repository's own `media` image field sets **`storeOriginalFilename: false`**
   on purpose (`sanity/schemas/media.ts`; CLAUDE.md notes a filename "may carry
   sensitive information"), so an asset uploaded through the real media-field
   path has **no `originalFilename`** to filter on. The Studio *Assets* pane and
   `client.assets.upload` do keep it, but recording the `_id` works regardless of
   which path is used.
4. **Only if you upload or query via an API/script path** (`@sanity/client`, the
   Sanity CLI): use a **temporary, Editor-role token**, minted for this run and
   revoked immediately after — never the app read token or a seed token. The
   **Studio uploader and the Vision plugin authenticate with your logged-in
   Studio session** (`docs/sanity-setup.md`), so the representative path needs no
   token at all; don't mint one you won't use.
5. **Do not commit** the project id, dataset name, or any token. Note them
   against AB#54 in Azure Boards if they need to be recorded at all, the same
   ownership boundary `docs/sanity-setup.md` draws for every other Sanity
   credential.

### E. Capture the verbatim outputs (AC3)

For **each** exported file, capture two things:

1. **The file's own metadata.** Run a **full-group dump** — one of these two, not
   a narrower command, because AC3 needs XMP *and* IPTC *and* EXIF from the same
   file:
   - `exiftool -G -struct -j control.jpg flat.jpg hierarchical.jpg` (best — JSON,
     groups, preserves the `lr:HierarchicalSubject` structure), or
   - `exiftool -a -u -G1 <file>` (the same coverage, human-readable).

   Optionally **also** capture the raw XMP packet with `exiftool -xmp -b <file> >
   file.xmp` — useful for seeing byte-level encoding, but it is an *addition* to
   the full dump, not a substitute (it contains no IPTC IIM or EXIF).

   Paste the **full** output, making sure these are all visible: `XMP-dc`
   (`Subject`, `Title`, `Description`), `XMP-lr` (`HierarchicalSubject`), `IPTC`
   (`Keywords`, `Caption-Abstract`, `Headline`), and `EXIF`/`IFD0` copyright and
   artist — so the sentinel round-trip is checkable.

2. **The Sanity asset document** the upload created. In the Vision plugin or via
   the API, run (published perspective is fine), using the `_id`s recorded in
   step D.3:

   ```groq
   *[_id in [
     "image-…-jpg",   // control
     "image-…-jpg",   // flat
     "image-…-jpg"    // hierarchical
   ]]
   ```

   Paste the **whole** returned document(s) verbatim — `metadata`, `mimeType`,
   `originalFilename` (if present), everything — with **one** redaction: in the
   `url` and `path` fields, replace the deployment-specific
   `…/images/<projectId>/<dataset>/…` segments with the literal placeholders
   `<projectId>` and `<dataset>`, and leave the rest of the value (the
   `<assetId>-<w>x<h>.<ext>` filename) intact. The project id and dataset are not
   secrets but the repository deliberately names neither (`docs/sanity-setup.md`),
   and they are not needed for any finding here.

3. Also export the scratch catalog's keyword list: **`Metadata ▸ Export
   Keywords…`**. Because the catalog is fresh (step A.1), the whole file is just
   the spike's sentinels — paste it **in full**, and note its exact structure
   (indentation character; how synonyms and "do not export" keywords are marked —
   bracket characters — in your version). If you had to reuse an existing
   catalog, paste **only** the sentinel subtrees (`Nature`, `Places`,
   `Työversio`) and drop every other line.

## `dc:subject` and `lr:hierarchicalSubject` survival (AC4)

**Hypothesis, to confirm or overturn with the data above:**

- **In the exported JPEG:** both survive. Lightroom writes flattened keywords to
  `XMP-dc:Subject` (and, depending on version and the export "Include" level,
  also to IPTC IIM `Keywords`, 2:25 — recent Lightroom does not always write the
  IPTC copy, which is one thing the dumps confirm), and — when *Write Keywords as
  Lightroom Hierarchy* is on — writes the pathed form to the Adobe-namespace
  `XMP-lr:HierarchicalSubject` as an `rdf:Bag` of `Parent|Child|Leaf` strings.
  The XMP values are plain UTF-8 inside the packet.
  ([community.adobe.com](https://community.adobe.com/t5/lightroom-classic-discussions/dc-subject-lr-hierarchicalsubject-adobe-bridge/m-p/9522790),
  [lightroomqueen.com](https://www.lightroomqueen.com/community/threads/write-keywords-as-lightroom-hierarchy.54767/#post-1368466))
- **Into Sanity:** **neither survives into the asset document.** Sanity's image
  pipeline extracts only `dimensions` / `hasAlpha` / `isOpaque` (always),
  `lqip` / `blurhash` / `thumbhash` / `palette` (default), and `image` / `exif` /
  `location` (opt-in). None of those carries IPTC or XMP subject/keyword fields,
  and `exif` is camera-settings only.
  ([sanity.io/docs/apis-and-sdks/image-metadata](https://www.sanity.io/docs/apis-and-sdks/image-metadata))
  The original file is still retrievable from `asset.url` after upload, so the
  keywords are not *lost* — they are just not *indexed by Sanity*.

**Conclusion:** _(pending the recorded asset document — confirm nothing
keyword-bearing appears under `asset.metadata`.)_

## Seeding the vocabulary from a Lightroom keyword export (AC5)

**Hypothesis, to confirm with the `Export Keywords…` output:**

Lightroom's `Metadata ▸ Export Keywords…` produces a **tab-indented plain-text
tree**: one keyword per line, depth by leading tab count, so the parent/child
structure is fully recoverable. Synonyms and "do not export" terms are flagged
with bracket characters (record which). This file is a plausible **one-time
seed** for AB#56's controlled vocabulary (parse the tree → one keyword document
per line, `parentKeywordId` from indentation), but **not** a sync source — it has
no stable ids, so a second export cannot be diffed against the first without a
name-match heuristic.

precomposed (NFC, `U+00E4`) or decomposed (NFD, `a` + `U+0308`) in the file and
in the keyword export.)_

## Recommended extraction point and Node dependency (AC6)

### Where extraction runs

If the AC4 conclusion holds (Sanity stores no keyword data), extraction **cannot**
be "read it back off the asset document". The realistic options:

| Option | How | Verdict |
| --- | --- | --- |
| **A. Owner-run pre-upload import script** reads the **original files** and writes keyword references onto the media documents (or a staging doc) before/around the Studio upload | a `scripts/*.mts` in the existing owner-run tooling family (`seed:sanity`, `recompute:shuffled-order`) | **Recommended.** Only point with guaranteed access to the *complete* original metadata; no app or CI runtime cost; matches an established project pattern; a heavy parser dependency here is tooling weight, not shipped weight. |
| B. Studio custom asset source / input plugin parses the file **in the browser at upload time** | a Studio plugin using an isomorphic parser | Possible, but puts a parser in the Studio bundle, couples ingest to Studio, and a WASM/JS XMP parser in-browser is the least-proven path. Revisit only if a no-script upload workflow is a hard requirement. |
| C. Post-upload **Sanity Function / webhook** re-fetches `asset.url` and parses server-side | serverless function on `asset.create` | Works, but adds infra AB#83's webhook story does not currently cover, and re-downloads every asset. Heavier than A for no ingest-quality gain. |

**Recommended: Option A** (see the consolidated recommendation below). The
recorded asset document is expected to confirm Sanity stores nothing
keyword-bearing; if it surprises us and carries usable keyword data, that would
*reduce* how much Option A has to do, not change which option wins.

**Recommendation:**

- **Extraction point: Option A** — an owner-run pre-upload `scripts/*.mts` that
  reads the original files. It is the only point with guaranteed access to the
  complete original metadata, adds no app or CI runtime cost, and sits in the
  established owner-run tooling family.
- **Node dependency: `fast-xml-parser` (5.x, MIT) plus a ~40-line hand-written
  JPEG APP1/XMP-packet reader.** It honours the "minimal dependencies" hard rule
  — one small, current, actively-maintained MIT dependency with no native binary
  and no child process — and Lightroom's `dc:subject` / `lr:hierarchicalSubject`
  are a fixed, well-documented `rdf:Bag` shape, not an open-ended parsing
  problem. `exifr`, the obvious off-the-shelf pick, is **rejected**: unmaintained
  since 2022-05.
- **Fallback: `exiftool-vendored` (37.x)** — adopt it instead only if the
  recorded dumps show one of: (a) XMP structure or encoding the hand-rolled
  reader would misparse, or (b) photographs whose keywords appear **only** in the
  APP13 IPTC IIM block with no `dc:subject` copy (which an APP1 reader cannot
  see). Its 21–35 MB vendored binary + subprocess is an owner-run tooling cost,
  never shipped to a browser — the same posture the project takes toward
  `@terrastruct/d2` — but it is still a heavier dependency than the primary pick,
  so it is the exception, not the default.

The measurement can **confirm or trigger the fallback**; it does not reopen the
choice. Whichever lands, **AB#55/56 record it in `docs/asset-inventory.md`** (and
`NOTICE`/`licenses/` if attribution attaches) at that point — this spike adds no
dependency itself.
